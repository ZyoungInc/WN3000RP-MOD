# 常驻控制页、临时模式切换：离线可行性记录

状态：用户已改选电脑本地脚本；此页保留离线研究结论，不作为当前实施计划。未写设备 Flash。当前工具是 `tools/mode_switch.py`。

目标：设备正常开机仍运行原厂 PSR；设备自身提供手机浏览器可访问的模式控制页。按“Wi-Fi STA → NAT → 有线”或“有线 → AP”时只改变 RAM 中的接口、桥、进程和地址；重启恢复 PSR，但控制页依然存在。控制页代码、两种模式脚本与原有固件一同保存在 Flash。当前**没有制作可刷入镜像，也没有写 Flash/NVRAM**。

## 本机镜像事实（2026-10-04）

- 原厂 `linux` 分区 `0x2f0000` = 3,080,192 B；原厂 `.chk` 的 58 B NETGEAR 头之后 Linux 数据为 2,969,600 B，分区尾部 110,592 B 为填充。镜像已有分区前缀与只读 Flash dump 一致。
- 根文件系统起于 Linux 分区偏移 `0xBD91C`。`mtd2` 分区 2,303,716 B；SquashFS superblock 的实际文件系统长度为 2,190,382 B，尾部约 113,334 B。它是非标准 `shsq` SquashFS 3.0/LZMA，普通 `mksquashfs` 4.6.1 不能直接生成兼容镜像。数字说明*可能*容纳小程序，不能把尾部空白直接当作可写目录。
- `/dev/root` 是只读 SquashFS。`/sbin/init`、`/sbin/preinit` 都链接到 `/sbin/rc`；没有可直接编辑的 `rcS` 开机脚本。因此页面常驻需要重打包固件，并实现经过验证的启动入口。只向 `/tmp` 上传，重启必然消失。
- 原厂 `httpd` 是专用二进制，暂未确认有安全的自定义 CGI 注册入口；可考虑另起小型控制服务（例如 8080），但其开机启动同样要解决。控制服务应要求认证；只按白名单执行固定动作，不接收任意 shell 命令。

## 拟定实现与验证顺序

1. 先将控制服务、页面与模式脚本在**设备 RAM** 中完整试运行。验证从手机浏览器操作、模式切换、管理地址迁移、失败自动重启和两种模式本身。启动时原厂 PSR；所有控制操作只改 RAM。
2. 找到能生成该设备 `shsq` SquashFS 3.0/LZMA 的可靠打包器；离线重包*未改动* rootfs，校验解包内容、权限、链接及镜像布局。随后加入极小的控制文件并测体积。不能用现代 SquashFS 4 镜像直接替换。
3. 离线确定、实现并验证启动入口，保留 `/sbin/rc` 原有 PID 1、参数和启动顺序语义。不能仅把 `/sbin/rc` 改名再用普通 shell 脚本调用，因为程序可能依赖 `argv[0]`。
4. 构造 `.chk` 所需 NETGEAR 头、长度和校验，离线核对型号、分区边界与校验。制定从原厂固件恢复的方法，确认设备进入恢复模式的实测步骤；必要时再讨论 TTL。
5. **实际写 Flash 前暂停**，逐项说明将写哪个分区、镜像 SHA-256、启动改动、测试证据、失败/恢复路径。用户最初要求所有永久 Flash 写入前先说明；此前允许“控制页可以写进设备”只确定了方案方向。

## 两个按钮的现有限制

- WISP/NAT 目前依赖在测试热点写死的 `192.168.157.22`、网关 MAC，且只处理部分 IPv4 TCP/UDP/ICMP；没有上游 DHCP 续租、IPv6、分片和长期稳定性证明。固化控制页不等于该 NAT 程序已经适合日常使用。
- 有线 → AP 的桥接已在 RAM 短时验证；首次让 STA `disassoc` 后原厂服务重建 PSR，触发原因待查。暂可保留 STA 关联但将它移出桥。真正有线上游的管理 IP/DHCP 要按其网段处理，测试时的 `10.42.57.2` 不能普遍写死。
- 模式切换后控制页地址可能变化；页面应显示新地址，切换前启动独立回退定时器。重启始终返回原厂 PSR；控制页仍可在原厂管理 IP 的另一个端口访问。
